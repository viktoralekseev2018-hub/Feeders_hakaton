# Архитектура и границы реализации

## Решение

Бэкенд хоста — подходящий каркас. Для трёх участников достаточно одного Go-процесса
с независимыми пакетами и явной сборкой зависимостей. Микросервисы и сервер рендеринга
не нужны. Ollama позднее запускается отдельным локальным процессом. Хост играет
через тот же браузерный клиент, что и остальные; рендеринг — на каждом ноутбуке.

```text
Браузеры хоста и LAN → HTTP / WS → Go host
                                  ├─ Auth → Accounts → FileStore
                                  ├─ Realtime → game.Module → World.Service
                                  │                 │              │
                                  │              Players ←─────────┘
                                  └─ Static files (embedded)

World → Publisher → Realtime → выбранные игроки
Будущий agents.Service → локальная Ollama / локальный алгоритм
```

Требования задания хакатона имеют приоритет. `main__task.txt` обрывается в начале
этапа 2; прошлый чат — контекст, а не распоряжение создать PR или реализовать сцену.
Каркас учитывает фактический JS-клиент и его сообщения. Переход на TS/Vite не
навязывается одновременно с серверной интеграцией.

## Реализованные границы

- `cmd/game-server`: сборка зависимостей, конфиг, логирование, LAN, остановка HTTP
  и отдельно hijacked WebSocket.
- `internal/auth`: нормализованные имена, bcrypt, постоянные аккаунты, случайные
  сессии, HttpOnly/SameSite cookie. До четырёх параллельных bcrypt-операций, затем
  429. Сессии истекают и отзываются, на диск не сохраняются.
- `internal/realtime`: сессия проверяется до Upgrade; один сокет на аккаунт;
  один reader/один writer; очередь 64 сообщения с отключением медленного клиента;
  вход ≤8 KiB, до 60 сообщений/с с всплеском 120; ping каждые 25 с, pong до 60 с,
  запись до 5 с. Политика не требует изменений в World.
- `internal/game`: init/input и вызов World через интерфейс; без World выдаёт
  capabilities=false. Непроверенные координаты не сохраняются как состояние.
- `internal/storage`: файл на аккаунт/игрока, mutex внутри процесса, запись через
  временный файл, Sync и Rename. Повреждённые данные не обнуляются молча.
- `internal/server`, `web`: маршруты, same-origin, embedded клиент, SPA fallback
  только для HTML-навигации. Отсутствующие API/файлы не возвращают HTML с кодом 200.

Файловое хранилище рассчитано на **один процесс на каталог**. Это не транзакционная
БД: нет межпроцессного lock, гарантий сохранности каталога при потере питания или
транзакции между аккаунтом и состоянием. При необходимости оно заменяется через
`storage.Accounts` / `storage.Players`, например на SQLite.

## Подключение независимых модулей

### Dev 1: World и сохранения

Реализуйте `world.Service` в `internal/world`. Возможный конструктор:
`world.New(repo storage.Players, publisher world.Publisher)`. В `main.go` замените
`game.New(repo, nil, log)` на `game.New(repo, worldService, log)`. World не должен
импортировать пакет realtime: исходящие события идут через `world.Publisher`.

1. `Join(ctx, user, savedState)` возвращает авторитетное состояние. Ошибка не должна
   оставлять частично зарегистрированного игрока.
2. `Input(ctx, playerID, input)` проверяет скорость, границы, столкновения и порядок
   `seq`. Координаты клиента — предложения. Новый сокет начинает sequence заново:
   сбрасывайте фильтр в Join, а не блокируйте перезаход сохранённым last_seq.
3. `Leave(ctx, playerID)` сохраняет состояние и освобождает ресурсы. Вызывается
   после обработки входящих сообщений и до допуска нового сокета этого игрока.
4. Сохраняйте принятые состояния периодически, а не только при Leave: процесс
   может аварийно завершиться. Не записывайте файл на каждый сетевой пакет.
5. `publisher.Publish(id, "world.snapshot", payload)` отправляет событие выбранному
   игроку. Payload сначала согласуется. `false` означает отсутствующего/медленного
   клиента; симуляция не ждёт сеть.

Разные игроки обрабатываются параллельно, один игрок — последовательно. World
защищает общее состояние mutex или собственной очередью. Фоновые задачи требуют
собственного жизненного цикла и завершения при остановке. Leave получает отдельный
контекст до 5 с, поскольку контекст сокета уже отменён.

### Dev 2: Realtime и локальный AI

Регистрируйте `hub.Handle("agent.talk", handler)` **до запуска сервера**. Handler
получает `Session.User()` из cookie; ID из payload не принимается.
`Session.Send(type, requestID, payload)` отвечает инициатору,
`hub.Publish(playerID, type, payload)` отправляет событие выбранному игроку.
`Hub.OnDisconnect` принадлежит `game.Module`: cleanup новых модулей добавляйте
в эту склейку, не перезаписывайте callback независимо.

`agents.Service` принимает `(PlayerID, AgentID, Text)` и возвращает Reply. Реализация
хранит историю/прогресс отдельно для игрока и персонажа, использует только локальную
модель или алгоритм. Модель скачивается заранее. AI нельзя выполнять в tick мира
или надолго блокировать reader: нужна ограниченная очередь/worker, ответ с исходным
request_id, таймаут и отмена при disconnect. Память NPC, Ollama-клиент и agent.talk
пока не реализованы. MCP для задания необязателен; будущий `cmd/mcp-tools` должен
вызывать те же доменные сервисы, не создавать второе состояние мира.

### Dev 3: клиент

HTTP login/register → same-origin WebSocket → init → player.ready. Браузер сам
прикладывает cookie к WebSocket: `credentials` есть у fetch, не у конструктора WS.
После player.ready примените сохранённую позицию/ориентацию к контроллеру и учитывайте
capabilities. Восстановление позиции в сцене — следующая задача владельца клиента.
Пока World отсутствует, NetworkManager не отправляет движение.

Для независимой UI-разработки явно импортируйте `MockNetworkManager` из
`contracts/mock-network.js` в dev-entry с Vite. Он не включается при ошибках реального
сервера. Для будущего мира сначала согласуйте примеры снапшотов, затем расширьте mock.

При переходе на Vite сборка размещается в web/dist; `go build -tags webdist` встраивает
только её. Ассеты локальные, без CDN. По умолчанию встраиваются четыре существующих
пути клиента; данные, Go-файлы и node_modules не раздаются.

## AOI и ≤10% кеша: проект следующего этапа

Не отправлять весь мир при входе. Детальные payload ещё не входят в контракт v1:

- Сервер владеет каталогом чанков, версиями и размерами. Передаёт метаданные объёма
  мира и бюджет `floor(totalWorldBytes / 10)`, а не все объекты мира.
- AOI вычисляется по проверенной серверной позиции. Если область не помещается
  в бюджет, уменьшается радиус/детализация. Каждый чанк должен помещаться в бюджет.
- Клиент учитывает геометрию, текстуры и данные объектов. Общие ассеты считаются
  один раз. При выгрузке очищаются JS, GPU (`dispose`), IndexedDB/CacheStorage,
  если они используются. Для мировых ресурсов — `Cache-Control: no-store`.
- Eviction происходит **до** загрузки замены. In-flight данные входят в бюджет:
  `resident + inFlight <= budget`. Нельзя включить все модели мира в bootstrap.
- Снапшоты других игроков фильтруются по AOI. Сервер проверяет, клиент интерполирует.

Задание не уточняет метрику «10% данных». Байтовый учёт — выбранное проверяемое
правило, а не утверждение организаторов. До демонстрации согласуйте метрику и
покажите счётчик бюджета, включая переходы и отсутствие скрытого кеша всего мира.

## Совместная работа и ограничения

Изменение контракта включает Go/TS-типы, схему, примеры и тесты одним PR. Несовместимое
изменение требует новой protocol_version. Владельцы согласовывают общие файлы и
точку сборки main.go. Ветка `feat/host-backend-scaffold` сохранена; каркас сам не
создаёт коммитов или PR.

Прямой HTTP предназначен для доверенной LAN хакатона и не шифрует пароль в пути.
Для другого размещения нужны TLS и настройка cookie/origin; COOKIE_SECURE сам TLS
не включает. Сейчас сервер не доверяет X-Forwarded-* и не предоставляет wildcard CORS.
